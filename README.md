# BoundScript

**Human-designed. Agent-implemented. Bound by contracts.**

BoundScript is an experimental language for defining software systems through explicit architecture, component contracts, capability boundaries, and imperative orchestration.

It combines declarative system definitions with explicit control flow. Component implementations may be written by developers or generated by build-time AI agents, while the system's structure and execution flow remain explicitly defined.

This repository currently contains a minimal executable vertical slice: a Langium-based parser, deterministic compiler, artifact-driven runtime, and CLI. It supports minimal director-to-box invocation, but does not yet implement contract enforcement, imports, general control flow, sandbox enforcement, or agent-driven implementation.


## Direction

BoundScript is designed around the following principles:

- **Systems:** Declarative definitions of software systems and their architecture.
- **Boxes:** Isolated implementation units with explicit contracts, inputs, outputs, and capability requirements.
- **Directors:** Imperative orchestration with explicit control flow, including branching and repetition when required.
- **Modules:** Reusable types, contracts, and box definitions with explicit imports, independently of any particular system.
- **Implementations:** Components implemented by developers or build-time AI agents, behind defined contracts.
- **Capabilities:** Execution permissions enforced by a sandbox rather than trusted to prompts or static types.
- **Execution:** Explicit execution semantics without assuming all workflows are DAGs.
- **Independence:** No dependency on a particular LLM provider or agent framework.

BoundScript is not intended to replace general-purpose programming languages. Its purpose is to define systems, express component boundaries, and orchestrate implementations.

The execution target remains an open design decision. The current prototype compiles to versioned artifacts executed by a BoundScript runtime; generating JavaScript for Node.js is a potential future target.

Run the executable example:

```bash
npm run bound -- examples/hello-minimal.bound
```

Expected output:

```text
Hello, World!
```

See [`examples/hello-world.bound`](examples/hello-world.bound) for broader, non-executable syntax exploration.

## Director → Box invocation

After `npm install`, run this command from the repository root:

```bash
npm run --silent demo:director-box
```

It builds the TypeScript packages and demo host, then prints exactly:

```text
Hello, World!
```

`--silent` suppresses npm's command banner; build-tool output is sent to stderr. The [demo host](examples/director-box/host.ts) loads the real `.bound` source, parses and validates it, compiles with the explicit `Greeter` → `demo.greeter` binding, and executes the artifact with the separate [TypeScript Greeter](examples/director-box/greeter.ts) registered under that ID.

Running `npm run bound -- examples/director-box.bound` is **not supported**: the current CLI supplies neither compile-time box bindings nor runtime implementation registrations, so compilation reports `compiler.missing-implementation`. It does not load or discover TypeScript implementations. Use the demo host for this example; `npm run bound -- examples/hello-minimal.bound` continues to work without bindings.

[`examples/director-box.bound`](examples/director-box.bound) declares one string-in/string-out operation and invokes it from a director:

```boundscript
box Greeter {
    operation greet(name: string): string
}
```

Inside `on start`, `let greeting = Greeter.greet("World")` stores the result and `print(greeting)` consumes it. Boxes are declared before the director. Each box has exactly one operation, one named string input, and one string output. Calls accept only a string literal; variables can only hold call results and be passed to `print`. Variables are immutable and local to one execution.

Bind developer-provided TypeScript functions through the programmatic API:

```typescript
import { readFile } from 'node:fs/promises';
import { parseBoundScript } from '@boundscript/language';
import { BoundScriptCompiler } from '@boundscript/compiler';
import { BoundScriptRuntime } from '@boundscript/runtime';
import { greet } from './my-greeter.js'; // Developer-provided (string) => string | Promise<string>

const parsed = parseBoundScript({
  uri: 'examples/director-box.bound',
  text: await readFile('examples/director-box.bound', 'utf8')
});
if (!parsed.program) throw new Error(JSON.stringify(parsed.diagnostics));

const compiled = await new BoundScriptCompiler().compile(parsed.program, {
  Greeter: 'my-greeter' // Source box name → resolved host implementation ID
});
if (!compiled.ok) throw new Error(JSON.stringify(compiled.diagnostics));

const runtime = new BoundScriptRuntime(
  { writeLine: (value) => console.log(value) },
  { 'my-greeter': greet } // Implementation ID → trusted TypeScript function
);
await runtime.execute(compiled.artifact, { entrypoint: 'start' });
```

Every declared box requires an explicit binding. Unknown boxes, operations, and variables fail semantic validation/compilation. Missing host functions fail before instruction execution. Thrown/rejected implementation errors and non-string results fail execution with contextual errors. Functions are not generated, loaded dynamically, or embedded in the artifact; the host supplies them. They run **without sandbox enforcement**. The CLI has no implementation-loading option, so use the API for box programs; the existing Hello World CLI remains unchanged.


## Target use cases

The following are minimum **behavioral targets** for the language, not implemented features or finalized syntax:

| Target | Capability to demonstrate |
| --- | --- |
| [UC-01](docs/use-cases/01-system-box-execution.md) | A director invokes a bound box implementation and consumes its output |
| [UC-02](docs/use-cases/02-contract-enforcement.md) | Input and output contract violations produce identifiable failures |
| [UC-03](docs/use-cases/03-director-control-flow.md) | Branches and repetition control box execution |
| [UC-04](docs/use-cases/04-modules-and-imports.md) | Reusable declarations can be imported by multiple systems |
| [UC-05](docs/use-cases/05-capability-isolation.md) | The execution environment denies undeclared capabilities |

Each target includes success and failure criteria. See [the target use case index](docs/use-cases/README.md) for scope and acceptance guidance. These targets are independent of whether the eventual execution backend interprets artifacts or generates JavaScript.

## Repository layout

```text
packages/
  language/   Langium grammar, generated typed AST, parsing, and diagnostics
  artifact/   Shared executable-artifact contract between compiler and runtime
  compiler/   Deterministic resolved-input to artifact compilation boundary
  runtime/    Provider-neutral artifact execution boundary; does not know the source DSL
  sandbox/    Capability and resource policy definitions
  cli/        Source-to-parser-to-compiler-to-runtime command-line pipeline

  open-questions.md

  hello-minimal.bound
  hello-world.bound
  director-box.bound
tests/
  scaffolding.test.ts
  conformance.test.ts
  fixtures/
```

Build-time AI-agent orchestration remains deferred. Build-time agents are development tooling, not runtime components. Runtime agents, if supported later, will be explicit language-level application behavior and will remain provider-neutral.

## Development

Requirements: Node.js 22.12+ and npm.

```bash
npm install
npm run check
npm run build
```

npm 12 blocks unreviewed dependency install scripts by default. The current dependency graph requires no install-script approvals; new scripts will remain blocked until explicitly reviewed.

Langium-generated TypeScript sources are reproducible and ignored by Git. Build and test commands regenerate them from `packages/language/src/boundscript.langium`.

Useful commands:

- `npm run --silent demo:director-box` — build and run the bound TypeScript Greeter demo
- `npm run langium:generate` — regenerate the parser, typed AST, and language metadata
- `npm run typecheck` — generate language sources and compile all TypeScript project references
- `npm test` — run the Vitest suite
- `npm run check` — run type checking and tests
- `npm run clean` — remove TypeScript build outputs

## Status

The executable subset supports one `system`, optional boxes with one string-in/string-out operation each, one `director`, and one sequential `on start` block. Statements are string-literal box calls assigned with `let`, and `print()` with a string literal or previously assigned variable. No imports, general expressions, loops, conditionals, or testing syntax are supported. Use Vitest for external tests. The broader example language remains design material rather than a finalized specification.
